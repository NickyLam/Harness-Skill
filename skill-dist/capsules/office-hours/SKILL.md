# Office Hours — YC 合伙人产品诊断

> **设计模式**：Inversion（先挑战假设，再出方案）
> **阶段**：定义/规划
> **角色**：Product Owner
> **触发**：`/office-hours`

## 触发条件

| 触发场景 | 触发方式 | 说明 |
|---------|---------|------|
| 新功能方向不确定时 | 用户输入 `/office-hours` 或「帮我评估这个想法」 | 需要第三方视角审视需求价值 |
| 多个需求优先级冲突时 | 产品 backlog 拥挤需要裁剪 | 用六问框架做强制排序 |
| 进入新市场/新领域前 | 战略性决策点 | 避免投入错误方向 |
| 定期产品健康检查 | 每个迭代周期开始前 | 作为例行流程 |
| 团队对需求有分歧时 | 需要客观的仲裁框架 | 六问提供结构化讨论基础 |

**不触发场景**：技术实现细节讨论（走 brainstorming）、纯 Bug 修复、紧急生产事故处理。

**与 brainstorming 的关系**：
- **brainstorming** 回答「怎么实现」— 假设需求是正确的，专注于设计方案
- **office-hours** 回答「值不值得做」— 先质疑需求本身，再做方向判断
- **使用顺序建议**：先 `/office-hours` 确认方向 → 再 `/spec` 设计方案
- **替代场景**：当需求非常明确且无争议时，可跳过 office-hours 直接进入 brainstorming

## 前置依赖

| 依赖项 | 来源 | 必需性 | 说明 |
|-------|------|-------|------|
| 用户的需求描述 | 对话上下文 / 文档 | 必需 | 被评估的功能或需求描述 |
| 项目背景信息 | `.harness/config.yaml` 或对话 | 可选 | 了解项目当前阶段和资源约束 |
| 已有的数据指标 | 用户提供的业务数据 | 可选 | 用户量、收入、增长率等（如有） |
| 竞品信息 | 用户提供的竞品分析 | 可选 | 市场竞争格局参考 |

**前置检查**：如果用户无法清晰描述想要做什么，应先通过追问帮助其明确需求。

## 核心原则

1. **先挑战前提**：不假设需求是对的，先质疑
2. **用户视角**：站在最不满意的用户角度思考
3. **MVP 思维**：80% 效果的 20% 方案优先
4. **时间约束**：三个月后这个功能还存在吗？

## 执行流程

### Step 1：YC 六问采访（Inversion 模式）

⚠️ 在六个强制问题回答完毕之前，禁止给出最终建议。

严格按顺序提出以下六个问题，每个问题等待用户回答。每个问题包含详细说明和评判标准：

#### 问题 1：谁是你最不满意的用户？他们为什么不满意？

**详细说明**：
这不是问「你的用户是谁」，而是问「谁最不满意」。满意的用户不会驱动改进，只有痛得最深的人才能指出真正的痛点。

**评判标准**：
| 回答质量 | 特征 | 处理方式 |
|---------|------|---------|
| ✅ 优秀 | 能具体描述用户画像 + 具体痛点场景 + 当前解决方案的不足 | 继续下一问 |
| ⚠️ 一般 | 只说了用户群体但没说具体痛点 | 追问：「能举个例子吗？某个用户在什么场景下遇到了什么问题？」 |
| ❌ 模糊 | 回答「所有用户都不满意」或泛泛而谈 | 引导：「如果只能选一个最痛苦的用户，你会选谁？为什么？」 |

#### 问题 2：如果你只能解决一个问题，解决哪个？

**详细说明**：
这是强制优先级排序的问题。资源永远有限，必须做出取舍。这个问题迫使你面对残酷的现实。

**评判标准**：
| 回答质量 | 特征 | 处理方式 |
|---------|------|---------|
| ✅ 优秀 | 明确选出一个问题 + 说明为什么不选其他问题 | 继续下一问 |
| ⚠️ 一般 | 列出了多个问题但没做最终选择 | 追问：「如果预算只够做一个呢？你选哪个？」 |
| ❌ 逃避 | 说「这些问题都重要不能割舍」 | 强制二选一：「A 和 B 之间，选一个，现在就选」 |

#### 问题 3：这个功能上线后，你怎么知道它成功了？

**详细说明**：
没有衡量标准的目标不是目标，是愿望。成功的定义必须是可观察、可量化、有时间线的。

**评判标准**：
| 回答质量 | 特征 | 处理方式 |
|---------|------|---------|
| ✅ 优秀 | 包含具体指标（数字）+ 衡量方法 + 时间线 | 继续下一问 |
| ⚠️ 一般 | 有定性描述但缺定量指标 | 追问：「用什么数字来衡量？目标是多少？」 |
| ❌ 模糊 | 「用户会喜欢」「体验会更好」等主观表述 | 要求转化为：「DAU 提升 X%」「转化率从 A 提升到 B」「加载时间从 Xs 降到 Ys」 |

#### 问题 4：有没有更简单的方案能达到 80% 的效果？

**详细说明**：
这是防止过度工程的核心问题。大多数情况下，20% 的努力就能覆盖 80% 的用户需求。剩下的 80% 努力往往只服务最后 20% 的边缘场景。

**评判标准**：
| 回答质量 | 特征 | 处理方式 |
|---------|------|---------|
| ✅ 优秀 | 提出了一个更简单的替代方案 + 分析了效果折损 | 继续下一问 |
| ⚠️ 一般 | 承认可能有但没想清楚 | 引导 brainstorming：「如果我们砍掉 X 功能，影响多大？」 |
| ❌ 否定 | 「没有，当前方案已经是最简的了」 | 挑战：「如果只有一周时间而不是一个月，你会怎么做？」 |

#### 问题 5：做这个的时间能不能用来做更重要的事？

**详细说明**：
机会成本是隐形杀手。每个「是」都意味着对其他可能性的「不是」。这不仅是时间成本，更是团队注意力、士气和技术债务的机会成本。

**机会成本评估方法**：

```
机会成本 = 放弃的最佳替代方案的预期收益

评估步骤：
1. 列出当前团队在未来 N 周内可以做的其他 2-3 件事
2. 对每件事估算预期收益（用户价值 / 收入影响 / 技术积累）
3. 比较：当前需求的收益 是否 > 放弃的最大替代收益？
4. 如果 ≤ → 不值得做；如果 > 但差距不大 → 需要进一步论证
```

**评判标准**：
| 回答质量 | 特征 | 处理方式 |
|---------|------|---------|
| ✅ 优秀 | 列出了替代选项 + 做了量化比较 + 给出判断理由 | 继续下一问 |
| ⚠️ 一般 | 提到了替代选项但没有比较 | 追问：「那件替代事如果做了，收益大概是多少？」 |
| ❌ 盲目 | 「没有更重要的事了」 | 反问：「如果不做这个，你们接下来本来打算做什么？」 |

#### 问题 6：三个月后这个功能还存在吗？

**详细说明**：
这是长期价值验证。很多功能上线时热闹，三个月后无人问津。这个问题区分了「冲动需求」和「真实需求」。

**时间价值矩阵**：

| 时间维度 | 信号 | 含义 |
|---------|------|------|
| 1 周后 | 还在被积极使用和讨论 | 初步验证有效 |
| 1 月后 | 成为日常工作流的一部分 | 已经产生习惯价值 |
| 3 月后 | 无法想象没有它的状态 | 核心功能，高留存 |
| 3 月后 | 使用率下降 >50% | 可能是冲动需求或一次性需求 |
| 3 月后 | 已经被遗忘 | 浪费了开发资源 |

**评判标准**：
| 回答质量 | 特征 | 处理方式 |
|---------|------|---------|
| ✅ 优秀 | 有明确的使用频率预测 + 留存策略 | 进入诊断阶段 |
| ⚠️ 一般 | 有信心但缺乏依据 | 追问：「类似的功能之前做过吗？它们的生命周期是怎样的？」 |
| ❌ 不确定 | 「不知道 / 应该还在吧」 | 这是一个危险信号，建议降低优先级或先做 MVP 验证 |

### Step 2：MVP 判定框架

基于六问的回答，应用 MVP 判定框架决定范围：

```
该做的 MVP（坚决要做）
├─ Q1 有明确痛点用户 + Q2 有明确优先级 + Q3 有可衡量指标
├─ Q4 简化方案仍保留核心价值 + Q5 机会成本合理 + Q6 有长期价值
└─ → 输出：✅ 值得做，P0 优先级

该砍的需求（坚决不做）
├─ Q1 无明确痛点 / 痛点是「我觉得」而非「用户反馈」
├─ 或 Q3 无法定义成功指标
├─ 或 Q5 机会成本明显过高
└─ → 输出：❌ 暂不做，放入 idea backlog

需要调整的（缩小范围后再评估）
├─ Q4 发现可以做更简化的版本
├─ Q6 长期价值不确定但短期有价值
└─ → 输出：⚠️ 缩小为 MVP 范围，设定验证实验

MVP 范围裁剪规则：
1. 只保留解决 Q1 痛点的最小功能集
2. 砍掉所有「nice to have」但非「must have」的功能
3. 设定明确的 MVP 成功门槛（Q3 的指标）
4. 为 MVP 设定时间盒（建议 ≤ 2 周）
5. MVP 验证失败 → 砍掉；验证成功 → 进入完整版规划
```

### Step 3：输出诊断报告

基于六个回答和 MVP 判定结果，输出：

1. **诊断结论**：✅ 值得做 / ⚠️ 需要调整 / ❌ 暂不做
2. **优先级**：P0 / P1 / P2
3. **推荐方案**：简述（1-2 段）
4. **实施替代方案**：2-3 种，含工作量估算
5. **风险点**：主要风险 + 缓解策略

## 失败处理

| 失败场景 | 处理方式 | 恢复策略 |
|---------|---------|---------|
| 用户拒绝回答某一个问题 | 解释该问题的必要性，用不同方式重新提问 | 如果仍然拒绝，标注「N/A」并在报告中注明缺失项的影响 |
| 用户对所有问题都给出模糊回答 | 暂停六问，先引导用户做更深入的用户调研 | 建议进行用户访谈或数据分析后再重新启动 office-hours |
| 六问结论与用户期望严重冲突 | 尊重数据但承认局限性，呈现双方观点 | 最终决策权归用户，但记录 AI 的保留意见 |
| 无法获取量化数据支撑 Q3/Q5 | 使用定性替代方案 + 标注置信度低 | 建议「先做小规模实验验证假设」作为前置步骤 |
| 用户中途退出 | 保存已完成的问答到 `.harness/drafts/` | 下次从断点继续 |

## 交接协议

```markdown
## Office Hours 交接包

### 交付给 brainstorming（当诊断结论为 ✅ 或 ⚠️ 时）
- 诊断报告路径：`.harness/reports/office-hours-<topic>-YYYYMMDD.md`
- 诊断结论：✅ 值得做 / ⚠️ 需要调整（附 MVP 范围）
- 优先级建议：P0 / P1 / P2
- 关键约束：从六问中提取的设计约束（如时间限制、简化要求）

### 交付给 writing-plans（跳过 brainstorming 直接进入计划时）
- MVP 范围清单（如适用）
- 成功指标定义（来自 Q3）
- 排除事项列表（被砍掉的功能点）

### 存入 idea backlog（当诊断结论为 ❌ 时）
- 需求描述 + 诊断结论
- 未来重新评估的触发条件（如「当用户量达到 X 时重新考虑」）
```

**交接验证**：接收方确认诊断报告存在且诊断结论字段不为空。

## 质量门禁

| 门禁项 | 检查方式 | 通过标准 |
|-------|---------|---------|
| 诊断报告存在 | 文件系统检查 | `.harness/reports/` 下有对应 office-hours 报告 |
| 包含全部六问回答 | 内容搜索 | 报告中包含 Q1-Q6 全部 6 个问题的回答记录 |
| 有明确诊断结论 | 内容搜索 | 出现「✅」或「⚠️」或「❌」判定标记 |
| 有优先级评定 | 内容搜索 | 出现 P0/P1/P2 优先级标记 |
| MVP 范围（如适用） | 内容搜索 | 当结论为 ⚠️ 时，必须有 MVP 范围章节 |
| 行数达标 | 行计数 | SKILL.md 本身 ≥ 50 行（v3 标准） |
