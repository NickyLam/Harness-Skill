# Memory Management — 记忆管理（三层可观测性增强版）

> **层级**：治理层 (Governance) — 知识层支撑
> **触发**：每次任务完成、每次错误、每次 /review、每次 /ship
> **设计模式**：Pipeline（写入 → 检索 → 蒸馏 → 固化）
> **灵感来源**：AHE Experience Observability — 将原始轨迹蒸馏为分层、可钻取的证据语料库

## 核心原则

1. **写入即承诺**：写入 memory 的内容必须准确、可追溯
2. **三层蒸馏**：原始层(Raw) → 详细层(Detail) → 摘要层(Summary)，支持从摘要钻取到原始
3. **检索优先**：遇到同类任务先查 memory，不重复踩坑
4. **定期蒸馏**：30 天以上的原始层必须提炼到摘要层后归档
5. **溯源链接**：每条摘要结论必须可追溯到原始记录

## 三层记忆架构

```
┌─────────────────────────────────────────────┐
│  摘要层 (Summary) — MEMORY.md               │
│  默认读取层 · 精炼规则和决策                  │
│  每条结论有 trace_id 指向详细层               │
├─────────────────────────────────────────────┤
│  详细层 (Detail) — daily logs + 证据报告     │
│  按需钻取 · 包含完整上下文和决策过程           │
│  每条记录有 trace_id 指向原始层               │
├─────────────────────────────────────────────┤
│  原始层 (Raw) — 完整执行轨迹                 │
│  完整保留 · 约 10K+ token 的原始交互记录       │
│  仅在需要深入分析时钻取                       │
└─────────────────────────────────────────────┘
```

## 记忆文件体系

```
.workbuddy/memory/
├── MEMORY.md                    ← 摘要层（curated，默认读取）
├── daily/
│   └── YYYY-MM-DD.md           ← 详细层（append-only）
├── traces/
│   └── {trace_id}.md           ← 原始层（完整轨迹）
└── archive/                    ← 归档（已蒸馏的原始层）
```

## 写入规范

### 原始层（每次任务执行时自动写入）

```markdown
# Trace: {trace_id}

**时间**: YYYY-MM-DD HH:MM
**阶段**: /harness <stage>
**角色**: <角色名>
**任务**: <任务描述>

## 执行轨迹
<完整的交互记录，包含工具调用、输出、决策过程>

## 关键决策点
| 决策 | 原因 | 替代方案 |
|------|------|---------|
| ... | ... | ... |

## 结果
- 成功/失败/部分成功
- 产出文件路径
```

### 详细层（每次任务完成后追加到 daily log）

```markdown
### HH:MM — <任务简述> [trace:{trace_id}]

**执行**：<做了什么>
**结果**：<成功/失败/部分成功>
**关键决策**：<为什么选这个方案>
**踩坑**：<遇到的问题和解决方法>
**经验**：<下次遇到同样情况该怎么做>
```

### 摘要层（定期蒸馏到 MEMORY.md）

```markdown
- **{规则标题}**：{精炼规则} [source:trace:{trace_id}]
```

## 钻取机制

当遇到问题时，按层级钻取：

```
1. 读取 MEMORY.md（摘要层）→ 找到相关规则
2. 如果规则不够详细 → 通过 [source:trace:{id}] 钻取到详细层
3. 如果需要完整上下文 → 通过 [trace:{id}] 钻取到原始层
4. 分析原始轨迹 → 更新摘要层的规则
```

### 钻取示例

```markdown
<!-- 摘要层 MEMORY.md -->
- **异步状态更新**：回调中不要直接读取旧 state，使用 dispatch 或 ref [source:trace:20260428-003]

<!-- 详细层 daily/2026-04-28.md -->
### 14:30 — 修复 useTodos Hook 状态不同步 [trace:20260428-003]
**踩坑**：Date.now() 在快速连续调用时可能产生重复 ID
**经验**：使用 idCounter + useRef 确保唯一性

<!-- 原始层 traces/20260428-003.md -->
<完整的调试过程、代码修改、测试运行记录>
```

## MEMORY.md 更新规则

| 触发条件 | 更新内容 | 示例 |
|---------|---------|------|
| 技术决策 | 记录决策和原因 | "选用 Vitest 而非 Jest：Vite 原生支持 [source:trace:20260428-001]" |
| 踩坑经验 | 记录问题和解决方案 | "异步回调中读取旧 state，需使用 dispatch 或 ref [source:trace:20260428-003]" |
| 项目约定 | 记录团队规范 | "所有 Hook 测试放在 src/__tests__/hooks/ [source:trace:20260428-002]" |
| 用户偏好 | 记录用户习惯 | "用户偏好中文输出 [source:trace:20260428-004]" |
| Skill 效果 | 记录 Skill 命中率 | "TDD Skill 在 reducer 测试中命中率 100% [source:trace:20260428-005]" |

### 禁止写入的内容

- ❌ 临时文件路径
- ❌ 中间搜索结果
- ❌ 工具错误信息（除非有解决方案）
- ❌ 敏感信息（密码、密钥、token）
- ❌ 未经确认的事实

## 检索规范

### 遇到新任务时的检索流程

```
1. 读取 MEMORY.md（摘要层）→ 了解项目概况和约定
2. 读取最近 2 天的 daily log（详细层）→ 了解近期工作上下文
3. 搜索相关 Skill → 获取执行指南
4. 执行任务 → 写入原始层
5. 任务完成后追加到详细层
6. 定期蒸馏到摘要层
```

## 蒸馏规范（阶段蒸馏 + 启动时蒸馏）

> **灵感来源**: Claude Code KAIROS 模式 — 运行时 append-only，事后蒸馏
> **核心变更**: 从"每月蒸馏"改为"阶段完成时蒸馏 + 启动时补蒸馏"

### 蒸馏触发时机

| 触发时机 | 执行者 | 说明 |
|---------|--------|------|
| 阶段完成（Gate PASS） | 当前 Agent / Team Lead | 最主要的蒸馏时机 |
| 下次会话启动时 | 启动 Agent | 检查未蒸馏日志，补执行蒸馏 |
| 用户手动触发 | 任意 Agent | `/harness memory-distill` |

### 阶段蒸馏流程

1. **读取** 本阶段产生的日志条目（详细层）
2. **分类** 按主题分组（技术决策 / 踩坑 / 约定 / 偏好）
3. **提炼** 将具体事件转化为通用规则，附带 [source:trace:{id}]
4. **写入** 更新 MEMORY.md（摘要层）
5. **标记** 将已蒸馏的日志条目标记为 ✅ 已提炼

### 启动时蒸馏流程

1. 读取 MEMORY.md → 了解项目全貌
2. 读取最近 2 天的日志 → 了解近期上下文
3. 检查是否有未蒸馏的日志条目（无 ✅ 标记）
4. 如果有 → 执行蒸馏，更新 MEMORY.md
5. 开始执行用户任务

### 蒸馏质量检查

- [ ] 每条摘要规则是否有溯源链接？
- [ ] 溯源链接是否指向有效的 trace 文件？
- [ ] 是否有重复或矛盾的记忆？
- [ ] 已蒸馏的日志条目是否标记了 ✅？
- [ ] 敏感信息是否已清理？

### 运行时约束

- 运行时**禁止**更新 MEMORY.md（避免并行子代理写入冲突）
- 运行时**只追加**日志到详细层
- 多个子代理可以安全地并发追加到同一日志文件


## 失败处理

| 失败场景 | 处理方式 | 恢复策略 |
|---------|---------|---------|
| 记忆文件损坏 | 跳过该文件，从其他来源恢复 | 重新生成损坏的记忆文件 |
| 蒸馏后信息丢失 | 保留原始文件作为备份 | 调整蒸馏策略后重新执行 |
| 存储空间不足 | 清理过期的低优先级记忆 | 扩展存储或减少保留条目 |
| 并发写入冲突 | 使用文件锁或队列机制 | 重试写入操作 |
