# Gherkin Spec Generator — Gherkin .feature 生成器

> **所属 Capsule**: deep-requirements
> **生成器类型**: 产出物生成器 (Output Generator)
> **输入来源**: MODULE A (business-rules) + MODULE B (user-journey) + MODULE C (edge-cases)
> **输出格式**: Gherkin (.feature)

## 生成器职责

将业务规则、用户场景和边缘 case 转化为**可执行的 Gherkin 规格**，可直接被 Cucumber、Behat、pytest-bdd 等测试框架执行。

---

## 输入数据映射

| Gherkin 元素 | 数据来源 | 映射规则 |
|-------------|----------|----------|
| **Feature 名称** | 用户原始需求 | 提取核心功能名词 |
| **As a {role}** | UJ-Q1 用户角色 | 使用主要角色 |
| **I want to {goal}** | BR-Q1 业务目标 | 转化为用户目标语句 |
| **So that {value}** | UJ-Q4 成功指标 | 转化为业务价值 |
| **Scenario (happy path)** | UJ-Q2 核心旅程 | 主流程场景 |
| **Scenario (rule validation)** | BR-Q2 规则列表 | 每条关键规则一个场景 |
| **Scenario (exception)** | EC-Q1 异常清单 | 每类异常一个场景 |
| **Scenario (edge case)** | EC-Q3 边界限制 | 边界值场景 |
| **Scenario (concurrency)** | EC-Q2 并发策略 | 并发冲突场景 |

## 输出模板

```gherkin
# language: zh-CN
功能: {功能名称}

  作为 {主要用户角色}
  我想要 {用户目标}
  以便于 {业务价值}

  @p0 @smoke
  场景: 核心 happy path - {主流程描述}
    假设 用户已登录为"{角色}"
      且 系统"{前置条件}"已就绪
    当 用户执行"{核心操作}"
    那么 系统"{预期结果}"
      且 响应时间 < "{性能要求}"

  @p0 @smoke
  场景: 核心 happy path - {备选流程}
    假设 当前状态为"{初始状态}"
    当 用户执行"{操作}"
    那么 系统"{预期结果}"

  @p1 @regression
  场景: 业务规则验证 - {规则名称}
    假设 当前状态为"{初始状态}"
      且 规则"{规则ID}"的触发条件满足
    当 用户执行"{触发操作}"
    那么 系统"{符合规则的预期结果}"

  @p1 @regression
  场景: 业务规则验证 - {另一规则名称}
    ...

  @p1 @regression
  场景: 例外情况处理 - {例外类型}
    假设 当前状态为"{例外触发条件}"
    当 用户执行"{操作}"
    那么 系统显示"{友好错误消息}"
      且 记录错误日志包含"{关键字段}"

  @p2 @edge-case
  场景: 边缘 case - {边界条件描述}
    假设 数据值为"{边界值}"
    当 用户执行"{操作}"
    那么 系统"{边界处理结果}"

  @p2 @edge-case
  场景: 边缘 case - {另一边界条件}
    ...

  @p2 @concurrency
  场景: 并发处理 - {并发场景描述}
    假设 用户A正在"操作A描述"
      且 用户B同时执行"竞争操作B"
    当 系统检测到并发冲突
    那么 系统"{并发处理策略}"
```

## 场景生成规则

### 1. Happy Path 场景（@p0）

- 数量：1-2 个
- 来源：UJ-Q2 的核心旅程路径
- 特征：无异常条件，验证基本功能可用

### 2. 规则验证场景（@p1）

- 数量：按优先级生成（P0 规则必选，P1 选关键，P2 可选）
- 来源：BR-Q2 的业务规则表
- 特征：Given 包含规则触发条件，Then 验证规则执行结果

### 3. 例外处理场景（@p1）

- 数量：每类异常至少 1 个
- 来源：EC-Q1 的异常场景清单
- 特征：Given 设置异常触发条件，Then 验证优雅降级

### 4. 边缘 Case 场景（@p2）

- 数量：每个重要边界至少 1 个
- 来源：EC-Q3 的数据边界限制表
- 特征：使用精确的边界值（min, max, min-1, max+1 等）

### 5. 并发场景（@p2）

- 数量：0-2 个（如有并发需求）
- 来源：EC-Q2 的并发策略
- 特征：模拟多用户同时操作

## Tag 使用规范

| Tag | 含义 | 使用场景 |
|-----|------|----------|
| `@p0` | 最高优先级 | 必须通过的冒烟测试 |
| `@p1` | 高优先级 | 回归测试，每次构建运行 |
| `@p2` | 中优先级 | 边缘 case，定期运行 |
| `@smoke` | 冒烟测试 | 快速验证核心功能 |
| `@regression` | 回归测试 | 完整功能回归 |
| `@edge-case` | 边缘测试 | 边界值测试 |
| `@concurrency` | 并发测试 | 多线程/多用户测试 |

## 语法校验规则

生成的 .feature 文件必须符合：

1. **关键字正确性**:
   - 功能/场景/假设/当/那么 使用中文或英文（保持一致）
   - "且"（And）可用于扩展 Given/When/Then

2. **缩进一致性**:
   - 使用 2 空格缩进
   - Given/When/Then 子句对齐

3. **描述清晰性**:
   - 避免模糊词汇（如"合适"、"正确"、"正常"）
   - 使用可验证的具体描述

4. **步骤复用**:
   - 相似的场景应复用相同的 step 定义
   - 步骤参数化以提高复用率

## 输出文件规范

- **位置**: `.harness/features/{feature-name}.feature`
- **编码**: UTF-8
- **命名**: kebab-case（如 `user-authentication.feature`）
- **大小**: 建议 < 500 行（超过则拆分为多个文件）
