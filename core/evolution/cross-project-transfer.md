# Cross-Project Transfer — 跨项目迁移验证

> **灵感来源**：AHE 论文发现——冻结的 Harness 在跨模型家族迁移时仍保持增益
> **核心原则**：改进编码的是通用工程经验，而非项目特定的调参

## 概述

当 Harness 组件经过进化循环改进后，必须验证改进是否编码了通用工程经验（而非项目特定的过拟合）。跨项目迁移验证确保 Skill 体系的改进对所有项目有效。

## 验证流程

```
Skill 组件改进 → 在当前项目验证通过 → 在至少 1 个其他项目验证
                                              │
                                    ┌─────────┴─────────┐
                                    │                     │
                               迁移成功               迁移失败
                                    │                     │
                              保留改进              标记为项目特定
                              更新成熟度            不纳入通用 Skill
```

## 验证标准

### 通用改进（可迁移）

满足以下条件的改进视为通用改进：

- [ ] 在 ≥2 个不同项目中验证有效
- [ ] 改进不依赖特定技术栈（React/Java/Python 等）
- [ ] 改进不依赖特定项目结构
- [ ] 预测在新项目中同样成立

### 项目特定改进（不可迁移）

以下改进标记为项目特定，不纳入通用 Skill：

- 依赖特定库的 API 模式
- 依赖特定文件结构的路径引用
- 依赖特定测试框架的配置
- 仅在特定业务逻辑下有效的规则

## 迁移验证模板

```markdown
# Cross-Project Transfer Validation

**改进内容**: <什么改进>
**源项目**: <项目A>
**目标项目**: <项目B>

## 验证结果

| 指标 | 源项目 | 目标项目 | 差异 |
|------|--------|---------|------|
| Gate 通过率 | X/7 | Y/7 | ... |
| 任务完成率 | X% | Y% | ... |
| 错误率 | X% | Y% | ... |

## 结论
- [ ] 通用改进 — 纳入核心 Skill
- [ ] 项目特定 — 保留在项目级配置
- [ ] 需要调整 — 部分通用化后重试

## 调整记录（如需要）
<如何将项目特定的改进通用化>
```

## 迁移验证频率

| 触发条件 | 验证动作 |
|---------|---------|
| Skill 组件修改 | 下次在其他项目中使用时验证 |
| 进化循环完成一轮 | 选择 1 个其他项目验证 |
| 月度回顾 | 汇总所有迁移验证结果 |

## 与其他模块的协作

| 模块 | 协作方式 |
|------|---------|
| evolution | 进化循环产出的改进需经过迁移验证 |
| governance | 迁移验证结果纳入治理流程 |
| component-registry | 通用改进更新组件注册表 |
| memory-management | 迁移验证记录存入三层记忆 |
